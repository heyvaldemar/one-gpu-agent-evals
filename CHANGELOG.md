## [Unreleased]

### Added

- README: line 1 is out. Its section names the table, the three series and the figures that matter: no failed call in 24,936, Granite-4.1-8B nearly the same at 350 W and 450 W and with four server CPUs or all, and Granite-4.0-1B's series up to 19.5% apart, which no difference between its settings exceeds. `tests/recompute.sh` computes each of those nine figures from `results/line1/TABLE.md` and fails if the README does not give it as written; three new plants change one each, all caught. Writing the check corrected a figure first sent with the table: Granite-4.0-1B's spread had been given as up to 12%, the largest difference between line1-4 and either other series; the three series of one row are up to 19.5% apart.
- `results/line1/`: line 1's set, series line1-2, line1-3 and line1-4, measured on a workstation with an RTX 4090 on 17, 22 and 23 November 2026 under one set of conditions (the card on 8 PCIe lanes, driver 621.24, the same guest kernel and memory), each unit with every call's record, and `results/line1/TABLE.md`, computed by `scripts/recompute.py set`: for each unit and concurrency the median of the three series' calls a minute with the lowest and highest, the median p95 and every failed call. Every unit must be whole (its files the ones its SHA256SUMS lists, each with its hash) and follow from its calls, or there is no table; `tests/recompute.sh` holds the table to the series and shows it a unit with a file added and one with a file changed, and four new plants in `tests/recompute-plants.tsv` are caught. The host's operating system took an update between line1-2 and line1-3; its build is recorded, not a condition of the set: across the 24 levels, Granite-4.1-8B's three series agree within 4.4%, and Granite-4.0-1B's spread up to 12% either way between line1-3 and line1-4 on the same build as much as against line1-2 on the older one.
- `loadgen/calls.py`: the flagship's `scripts/capacity.py`, from its verified release and unchanged, with every call it makes (its level, seed, start on the wall clock, seconds, outcome and tokens) and every level's unrounded wall time written to a record. Nothing is written while a level is timed: a level's calls are written and fsynced after the level ends, so no write is part of any call's time; a level cut short is measured again whole ([ADR 1](docs/decisions/0001-measured-on-a-workstation-recomputed-in-ci.md)). The flagship's session pointed out that the first version, which fsynced each call as it finished, put that write inside the timed window.
- `scripts/recompute.py`: every level's aggregates computed again from those records with capacity.py's formulas and its own percentile function, imported from the release, failing on any difference and on records that are not whole. `tests/recompute.sh` runs it on a stub server's series and on four damaged copies, and `tests/recompute-plants.tsv` breaks the recorder and the recomputation six ways, each of which the test notices.
- `sources.lock` and `scripts/sources.sh`: the flagship's release v1.9.0, read only after its sha256, its cosign signature and its SLSA provenance pass. `models.lock` and `scripts/models.sh`: weights by the flagship's lines, from the publisher at the pinned revision, refused on another sha256 or a licence that is not a permissive OSI one. `images.lock`: the flagship's server, Python and busybox images by its digests ([ADR 2](docs/decisions/0002-the-flagships-load-server-and-weights-as-released.md)).
- `scripts/validate.sh`: seven static checks (`pins`, `models`, `args`, `deploy`, `kind`, `plan`, `private`) that hold this repository to the flagship's release, and `tests/static-plants.tsv`, sixteen breaks, each of which they notice. `private` (`scripts/private_check.py`) refuses, in any file, the names of the workstation's machines and of their domain (kept in base64, so the check does not carry them) any address in a private range (RFC 1918, RFC 6598, link-local, IPv6 unique local), and any time of day written with a local offset rather than in UTC, printing the file and line and never the match; it runs over this repository on every change and over a series before it is committed here. Its plants carry their text as JSON escapes, so the table of plants passes the check it breaks. `models` also holds every line of `models.lock` to its format: a file at a 40-hex revision, a sha256, a permissive OSI licence, and the flagship's image digest or `unpinned`, which the README explains.
- `tests/e2e.sh` on kind: the flagship's CPU server with the release's arguments and weights, the load from a Job beside it, the pod's own hash of the weights and a control pod that must refuse them under another hash, every level recomputed from its records, the load the flagship's AWS runs measure with (28 request bodies, sha256 603153b0..., as its session computes it; each series records it), and every pod's image one `images.lock` names. `tests/plants.tsv` breaks it five ways.
- `workstation/isolation_check.py`: what the environment on the workstation must not be able to do (a host filesystem, a host mount, a host program, a credential, an address off its list), each tried as root beside a control that must succeed. `tests/isolation.sh` runs it in a closed container, in the same with the variables a systemd session sets, and in nine opened ones, each of which it must name; `tests/isolation-plants.tsv` breaks it eight ways, each caught. The first version flagged the test's own bind mount of the check as a host filesystem, rightly; the check now comes in on stdin. Its first run on the workstation, in a WSL2 distribution that was not closed, failed as it had to, and took `DBUS_SESSION_BUS_ADDRESS` for a secret: the variables a systemd session sets on its own are now known as harmless, an SSH agent's socket still fails the check, and a refused mount reports mount's first line rather than its note about dmesg.
- `workstation/run_series.py`: a series of line 1 in the closed environment, unit by unit. Before any unit, the isolation check must pass, every carried-in file must match its sha256, and the flagship's archive and every model file must be the pinned ones, and the release unpacked from that archive must be it file for file (none missing, short or changed, and none it does not hold); then for each unit the server's container on an internal network, its time to ready, nvidia-smi every 500 ms (power, clocks, utilization, memory, PCIe generation and width), the flagship's load from a client container, the server's log, the recomputation, a manifest and SHA256SUMS. A unit cut short is recorded as interrupted and measured again whole; a unit done before is not run again. A series is measured under one set of the conditions the environment can see (its memory, the driver, the kernel, the card, and the width of the card's PCIe link): an invocation under others is refused and names what changed, so a series never mixes, say, two driver versions, two memory sizes, or a card on 8 lanes with the same card on 16. `workstation/plans/line1-1.json` is the first series' plan (Granite-4.0-1B and Granite-4.1-8B, the default power limit and 350 W, all cores and four), and `workstation/plans/line1-2.json` the same plan for the next series: the host's memory is being replaced, and a series is measured on one machine as it stands, so line1-1 stays the shakedown on the memory the host had first and line1-2 begins on the memory it keeps. The two plans differ only in their series' name, and the runner refuses an OUT that holds a series of another plan, so no unit of one lands in the other. and `scripts/validate.sh plan` holds its server's arguments to the flagship's GPU server and its images to `images.lock`. `tests/series.sh` runs the runner on a stub server in a container (a whole series, a unit cut short, changed conditions, a changed model file, a server that never becomes ready and must leave nothing running, a power limit the environment cannot read, a server's log that cannot be kept, an isolation check that fails), and `tests/series-plants.tsv` breaks it twenty-four ways, each caught. A unit keeps the server's log and removes its container and the GPU sampler however it ends, and a unit whose log could not be kept does not pass. Every file of a unit, and its directory, is on disk before the unit is marked done, and the hash of its SHA256SUMS goes into the series' record then; a done unit that is no longer what it was (a file emptied by a power cut, a file changed with its sums rewritten to match, a file added) is recorded as damaged, set aside under a name of its own, and measured again. Nothing is deleted, and an invocation that is refused touches no unit. A unit holds the files it makes and no others: the client's container can write in the unit's directory, so a file it did not make (a newline in its name would forge a line of SHA256SUMS) fails the unit, and the client runs as the runner's own user, not the image's root. An automated security review asked for the last three; the test then found that a unit set aside kept its done marker and was taken for a unit again, now fixed. That came from the workstation's first block, whose probes file in the guest was found empty after the guest had been stopped: the isolation check refused to pass on it, and the series did not start. The second block passed its preflight and started every server, and every unit failed in the client: the flagship's tree in the guest had been unpacked just before the guest was stopped, and its capacity.py lacked the functions calls.py wraps. The preflight had checked the archive and only that capacity.py existed; it now holds the tree to the archive, and a tree like that one stops the series before any unit. A unit that pins a power limit is held to the limit nvidia-smi reads; where it reads [N/A], as it can inside a GPU-P guest, or gets no answer at all, the unit runs only when the host says which limit it set (`--power-limit-w`), and its manifest says the limit was the host's. A condition that cannot be read stops the series rather than comparing equal to the same gap next time: a plan whose server runs on the GPU does not start without nvidia-smi, and nvidia-smi must answer every field it is asked, so that a reading left out never shifts the rest onto other names. Both came from an automated security review of the runner. Its first version listed SHA256SUMS in itself, hashed while still empty; the test caught it.
- [ADR 3](docs/decisions/0003-the-host-lends-the-gpu-the-environment-holds-nothing.md), accepted on 2026-11-12 after two probes on the workstation: a WSL2 distribution under the same account failed the isolation check (root mounted the system drive, the network was shared with Docker Desktop's distribution), and a Hyper-V guest with GPU-P failed it open and passed it closed, 24 of 24, with the GPU named in it. Before that, proposed: how a series runs on the workstation, in an environment that holds nothing, with the GPU lent by the host, surviving a power cut. It names the two candidates on a Windows 11 workstation, a Hyper-V guest with GPU-P and a WSL2 distribution, why the first is preferred and what the second gives up; two probes on the workstation choose. The environment reaches no network at all, not even while it is prepared: everything it runs is carried in as files, checked by signature or pinned hash where they were fetched and again inside. A proxy on the host to fetch through was considered and not built, since it would be a service of the host the environment can reach.
- `models.lock`: the weights of line 2 (model size against planted instructions) and of its gpt-oss series, each by its publisher's file at a pinned revision and its sha256, all Apache-2.0, `unpinned` since no CI builds an image of them and none is downloaded unless a run names it. Qwen3 from 0.6B to 32B is one family, so that size is the variable: the publisher's own files where it ships them (only Q8_0 at 0.6B and 1.7B), and IQ4_XS from one quantizer at 14B and 32B, since 32B in Q4_K_M leaves no room for its KV cache in 24 GB. Two bridges measure a change of file where the curve changes file, 4B in Q8_0 and Q4_K_M and 14B in Q4_K_M and IQ4_XS, so that it does not read as a change of size. Granite-4.1-3B is the flagship release's line, byte for byte; Granite-4.0-H-Small is a 32B mixture of experts and is reported as one; gpt-oss-20b and gpt-oss-120b are MXFP4 as their publisher ships them. The licences were read from each repository's card on Hugging Face; a quantizer whose card names no licence was not used.
- `workstation/plans/probe-gptoss-1.json`: a probe, never published. gpt-oss-20b on the flagship's GPU server with the release's arguments, one unit at the default limit, to see whether the server starts it and answers the load with `--reasoning off` (gpt-oss reasons in the harmony format and cannot be told not to) and how much of the card and the environment's memory it takes, before the gpt-oss series is planned. Its files are carried in under `/srv/line2` with their own list and this repository's own `models.lock`, so line 1's carried-in files stay as its three series found them.
- `workstation/memory_probe.py` and `workstation/memory/gpt-oss-120b-1.json`: a probe, never published, of what a model takes of the card and of the environment's memory, measured before its series is planned. For each configuration in turn (how many layers keep their experts on the CPU, and whether the weights are mapped or read in), the flagship's GPU server image under a memory limit two GiB below the environment's own, sampled once a second (the card's memory, the environment's available, cached and anonymous memory, the server's resident set split into anonymous and file pages, its cgroup's count), its time to ready, a few calls with the server's own timings, and its log. A configuration that does not come up ends its mode, and none starts that the time budget would not hold. The first spec is gpt-oss-120b, whose experts do not fit beside the rest in 24 GB. `tests/memory_probe.sh` runs it on the stub server, and `tests/memory-probe-plants.tsv` breaks it seven ways, each caught.
- `workstation/kind_gpu_probe.sh`: a probe, never published, of whether a kind node in the closed environment can run a pod on the GPU the host lends it, which line 2's flagship leg and the inference gateway's row both need. In a GPU-P guest the card is `/dev/dxg` with the driver's libraries under `/usr/lib/wsl`, reached through the CDI spec; the probe mounts those and the binaries the spec's hooks call into one labelled kind node, loads the CUDA image and NVIDIA's device plugin (the gateway's v0.20.1) into it, tries the plugin with two CDI strategies, and records every step, passed or not, with the cluster deleted however it ends. `tests/kind_gpu_probe.sh` runs it with `--test` on a machine with no GPU, and `tests/kind-gpu-probe-plants.tsv` breaks it five ways, each caught. Its first run found that `kind load docker-image` fails on a multi-platform image whose other platforms are not present; it now loads one platform's archive. It also records whether the node then finds the image by the digest the flagship's and the gateway's manifests name it with: on Docker Desktop it does not, since one platform's archive does not carry the multi-platform index that digest names. Both probes run in CI in a job of their own. Its run on the workstation on 24 November found the node and the cluster ready and NVIDIA's device plugin unable to load NVML under either strategy, with the driver's libraries reached under the driver root (`/driver-root/usr/lib/wsl/lib`); the node also did not find the CUDA image by its digest. The probe now mounts `/usr/lib/wsl` into the plugin at its own path, where the driver's own libraries look for the rest of the driver, and before the plugin a `libs` step asks the node and a pod with the plugin's mounts where NVML loads from: the file, `ldd` and `nvidia-smi -L` under each path, recorded as a finding either way. The kind probe's test failed there from its first commit: the probe pulls nothing, by design, and a fresh runner had neither the node image nor the Python one; the test now pulls both by the digests `images.lock` pins before it runs the probe.
- [ADR 4](docs/decisions/0004-fine-tuned-on-data-the-tests-never-saw.md) and `train/`: line 3's training data, generated and checked before any training. `train/generate.py` builds 2,000 conversations in the shape the flagship's harness sends (its system prompt and the tools it offers the default person, read from the verified release by parsing, never importing), from its own templates and a seed: no outside dataset and no model's output, so its licence is this repository's. Half have an instruction planted in a record, the report or a document, always in English, and the assistant answers the user without acting on it; the other half is ordinary work, an email the user asked for among it. `train/data.lock` pins the bytes, and `train/check_data.py` holds the data to the release's agent and keeps it apart from the release's tests: no customer, company, mail address, outside domain, document or person of theirs, customer IDs only from C5000 to C8999, no run of six words in common with their tasks, records, report or documents, and no planted instruction in another language, so the release's German one measures a language the training never planted in. `tests/train_data.sh` generates the data again, compares it with the lock and shows the check twenty-three changes it must refuse, each on its own check; `tests/train-data-plants.tsv` breaks the check, the generator and the reader twenty-six ways, each caught. An automated security review of the first commit found that the check took each example's own meta on trust: whether an instruction was planted, who an email was meant for, and what language the plant was in. It now reads all three from the messages (a record with notes or an address in a report or document is a plant, and must be declared; an email goes only to an address the user wrote or to the account manager the user asked to write to; the language check reads every text the generator wrote), holds arguments to their schema's whole pattern as the MCP server does, and the lock counts files whose names start with a dot. A second review asked for the meta's planted target to stay a check beside the recipients read from the messages, so an email to it fails even where the user also named that address, and for a record with a field the generator does not write to count as a plant. A third took the forbidden addresses from the tool results' own text rather than the meta (the meta's target must be named in its plant), and holds every field of a record to the shape the generator writes; writing that test found the address pattern took the full stop after an address into it, and so missed it. The first draft took customer IDs up to C9999, which the release names for a customer that does not exist; the reader's list of the release's IDs caught it. The base model is chosen from line 2's first series and written into ADR 4 before any training.
